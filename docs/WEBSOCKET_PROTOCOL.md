# Ermes WebSocket Protocol

**Status:** Draft  
**Protocol version:** 1  
**Transport:** WebSocket

## 1. Overview

The Ermes WebSocket protocol provides a persistent, bidirectional communication channel between an Ermes client and the Ermes backend.

It is designed for real-time interaction scenarios such as:

- text chat;
- streaming assistant responses;
- partial voice transcription;
- voice-triggered messages;
- draft text updates;
- response cancellation;
- future speculative generation;
- session reconnection and event recovery.

The protocol distinguishes between two kinds of messages:

```text
Client → Server    Commands
Server → Client    Events
```

A **command** expresses an intention:

> "Do this."

An **event** describes something that has happened:

> "This happened."

This distinction must be preserved even though both travel through the same WebSocket connection.

---

# 2. Architecture

The frontend connects only to `ermes-backend`.

```text
┌─────────────────────┐
│   ermes-frontend    │
└──────────┬──────────┘
           │
           │ WebSocket
           ▼
┌─────────────────────┐
│    ermes-backend    │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ ermes-orchestrator  │
│                     │
│ Runtime             │
│ EventBus            │
│ Agents              │
│ LLM                 │
│ Voice processing    │
└─────────────────────┘
```

Traditional HTTP endpoints should remain available for non-real-time operations such as:

- health checks;
- readiness checks;
- authentication;
- file uploads;
- conversation history;
- settings;
- other resource-oriented APIs.

The WebSocket is reserved for interactive real-time communication.

---

# 3. WebSocket Endpoint

Example development endpoint:

```text
ws://localhost:8091/v1/ws
```

Production should use TLS:

```text
wss://api.example.com/v1/ws
```

A WebSocket connection represents an active Ermes client connection.

A logical Ermes conversation is identified independently using a `session_id`.

---

# 4. Common Message Envelope

All protocol messages use a common JSON envelope.

Example:

```json
{
  "version": 1,
  "type": "message.commit",
  "id": "cmd_01JABC123",
  "session_id": "ses_01JABC456",
  "timestamp": "2026-11-21T19:30:00.000Z",
  "payload": {}
}
```

## Required fields

### `version`

Protocol version.

```json
"version": 1
```

Clients and servers must reject unsupported protocol versions.

---

### `type`

Identifies the command or event.

Examples:

```text
draft.update
message.commit
message.committed
assistant.message.delta
generation.cancel
```

The message direction determines whether the message is a command or an event.

---

### `id`

Unique identifier for this specific command or event.

Suggested prefixes:

```text
cmd_   client command
evt_   server event
```

Example:

```json
"id": "cmd_01JABC123"
```

IDs are useful for:

- tracing;
- logs;
- deduplication;
- correlation;
- debugging.

---

### `session_id`

Identifies the logical Ermes session.

```json
"session_id": "ses_01JABC456"
```

Multiple events and commands may belong to the same session.

---

### `timestamp`

UTC timestamp in ISO 8601 format.

```json
"timestamp": "2026-11-21T19:30:00.000Z"
```

For commands, the timestamp is generated by the client.

For events, the timestamp is generated by the server.

---

### `payload`

Contains message-specific data.

```json
"payload": {
  "text": "Hello Ermes"
}
```

The payload schema depends on `type`.

---

# 5. Optional Envelope Fields

## `correlation_id`

Links an event to the command or event that caused it.

Example:

```json
{
  "type": "message.committed",
  "correlation_id": "cmd_01JABC123"
}
```

This allows the client to associate:

```text
message.commit
      ↓
message.committed
```

---

## `sequence`

Monotonically increasing server-side event sequence number.

Example:

```json
"sequence": 205
```

`sequence` is only required for server events.

It is used for:

- ordering;
- detecting missing events;
- reconnecting;
- replaying events after temporary disconnections.

Commands sent by clients do not require a sequence number.

---

# 6. Identifiers

The protocol uses several domain-specific identifiers.

```text
session_id       Conversation/session
message_id       Committed chat message
draft_id         Mutable input draft
generation_id    Assistant generation process
utterance_id     Voice recognition utterance
```

These concepts must remain separate.

For example, a generation is not the same thing as an assistant message:

```text
generation
    │
    └── produces → assistant message
```

# 7. Client Commands

Initial protocol V1 defines the following commands:

```text
session.sync

draft.update
draft.cancel

message.commit

generation.cancel
```

# 8. `session.sync`

Sent after opening or reopening a WebSocket connection.

It tells the server which session the client wants to synchronize and which event it received last.

Example:

```json
{
  "version": 1,
  "type": "session.sync",
  "id": "cmd_001",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:00.000Z",
  "payload": {
    "last_sequence": 127
  }
}
```

For a new session or a client without previous state:

```json
{
  "version": 1,
  "type": "session.sync",
  "id": "cmd_001",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:00.000Z",
  "payload": {
    "last_sequence": null
  }
}
```

The server responds with `session.synced`.

If events after `last_sequence` are still available, they may be replayed before live delivery resumes.

---

# 9. `draft.update`

Updates a mutable user input draft.

Draft updates are not committed chat messages.

Example:

```json
{
  "version": 1,
  "type": "draft.update",
  "id": "cmd_002",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:01.000Z",
  "payload": {
    "draft_id": "draft_017",
    "revision": 4,
    "source": "keyboard",
    "text": "Explain how a neural net"
  }
}
```

A later revision:

```json
{
  "version": 1,
  "type": "draft.update",
  "id": "cmd_003",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:01.400Z",
  "payload": {
    "draft_id": "draft_017",
    "revision": 5,
    "source": "keyboard",
    "text": "Explain how a neural network works"
  }
}
```

The complete current draft text should be sent rather than character deltas.

This makes draft updates:

- idempotent;
- easier to recover;
- resistant to lost intermediate updates.

## Revision rules

Each update increments `revision`.

```text
revision 1
revision 2
revision 3
...
```

Older revisions must never overwrite newer revisions.

---

# 10. `draft.cancel`

Cancels an existing draft.

Example:

```json
{
  "version": 1,
  "type": "draft.cancel",
  "id": "cmd_004",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:03.000Z",
  "payload": {
    "draft_id": "draft_017",
    "revision": 5
  }
}
```

The server may emit:

```text
draft.cancelled
```

---

# 11. `message.commit`

Commits a final user message.

Example:

```json
{
  "version": 1,
  "type": "message.commit",
  "id": "cmd_005",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:04.000Z",
  "payload": {
    "draft_id": "draft_017",
    "revision": 5,
    "source": "keyboard",
    "text": "Explain how a neural network works"
  }
}
```

The complete text is included even if the server already knows the draft.

This makes a commit self-contained and auditable.

The server validates the draft revision where applicable and emits:

```text
message.committed
```

A committed message becomes part of the conversation history.

---

# 12. `generation.cancel`

Requests cancellation of an active assistant generation.

Example:

```json
{
  "version": 1,
  "type": "generation.cancel",
  "id": "cmd_006",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:07.000Z",
  "payload": {
    "generation_id": "gen_091"
  }
}
```

If cancellation succeeds, the server emits:

```text
generation.cancelled
```

# 14. `session.synced`

Confirms that the client session has been synchronized.

Example:

```json
{
  "version": 1,
  "type": "session.synced",
  "id": "evt_100",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:00.050Z",
  "sequence": 100,
  "correlation_id": "cmd_001",
  "payload": {
    "current_sequence": 100
  }
}
```

---

# 15. `draft.updated`

Confirms the server-side state of a draft.

Example:

```json
{
  "version": 1,
  "type": "draft.updated",
  "id": "evt_101",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:01.050Z",
  "sequence": 101,
  "correlation_id": "cmd_002",
  "payload": {
    "draft_id": "draft_017",
    "revision": 4
  }
}
```

This event does not necessarily need to be emitted for every draft revision in future high-frequency scenarios, but it is useful during the initial protocol implementation.

---

# 16. `draft.cancelled`

Indicates that a draft has been cancelled.

```json
{
  "version": 1,
  "type": "draft.cancelled",
  "id": "evt_102",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:30:03.050Z",
  "sequence": 102,
  "correlation_id": "cmd_004",
  "payload": {
    "draft_id": "draft_017"
  }
}
```

---

# 17. `voice.transcript.partial`

Represents the current speech recognition hypothesis.

Example:

```json
{
  "version": 1,
  "type": "voice.transcript.partial",
  "id": "evt_200",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:10.000Z",
  "sequence": 200,
  "payload": {
    "utterance_id": "utt_008",
    "text": "Ermes play music by",
    "activated": true
  }
}
```

A later hypothesis replaces the previous one:

```json
{
  "version": 1,
  "type": "voice.transcript.partial",
  "id": "evt_201",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:10.300Z",
  "sequence": 201,
  "payload": {
    "utterance_id": "utt_008",
    "text": "Ermes play music by Pink Floyd",
    "activated": true
  }
}
```

`text` contains the complete current hypothesis.

Clients must replace the previous partial transcript for the same `utterance_id`; they must not concatenate partial transcripts.

`activated` indicates whether the orchestrator currently considers the wake-word or activation condition satisfied.

The frontend displays this event but does not decide whether it should become a message.

---

# 18. `voice.transcript.final`

Indicates that speech recognition has finalized an utterance.

Example:

```json
{
  "version": 1,
  "type": "voice.transcript.final",
  "id": "evt_202",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:11.000Z",
  "sequence": 202,
  "payload": {
    "utterance_id": "utt_008",
    "text": "Ermes play music by Pink Floyd",
    "activated": true
  }
}
```

A final transcript is not necessarily a committed user message.

The orchestrator remains responsible for deciding whether an utterance becomes a message.

---

# 19. `message.committed`

Indicates that a user message has been accepted as part of the conversation.

The message may originate from several sources.

Possible initial values:

```text
keyboard
voice
```

Keyboard example:

```json
{
  "version": 1,
  "type": "message.committed",
  "id": "evt_203",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.000Z",
  "sequence": 203,
  "correlation_id": "cmd_005",
  "payload": {
    "message_id": "msg_042",
    "source": "keyboard",
    "text": "Play music by Pink Floyd"
  }
}
```

Voice example:

```json
{
  "version": 1,
  "type": "message.committed",
  "id": "evt_204",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.000Z",
  "sequence": 204,
  "payload": {
    "message_id": "msg_043",
    "source": "voice",
    "utterance_id": "utt_008",
    "text": "Play music by Pink Floyd"
  }
}
```

Keyboard and voice input converge at this event.

```text
keyboard ─┐
          ├──► message.committed
voice ────┘
```

After this point, message processing should not depend on the original input source unless explicitly required.

---

# 20. `generation.started`

Indicates that the orchestrator has started generating a response.

```json
{
  "version": 1,
  "type": "generation.started",
  "id": "evt_205",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.050Z",
  "sequence": 205,
  "payload": {
    "generation_id": "gen_091",
    "reply_to": "msg_043",
    "speculative": false
  }
}
```

A generation represents the execution process, not the assistant message itself.

---

# 21. `assistant.message.started`

Indicates that a new assistant message is being produced.

```json
{
  "version": 1,
  "type": "assistant.message.started",
  "id": "evt_206",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.100Z",
  "sequence": 206,
  "payload": {
    "message_id": "msg_044",
    "generation_id": "gen_091",
    "reply_to": "msg_043"
  }
}
```

The frontend should create an empty assistant message when this event is received.

---

# 22. `assistant.message.delta`

Streams incremental assistant output.

Example:

```json
{
  "version": 1,
  "type": "assistant.message.delta",
  "id": "evt_207",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.200Z",
  "sequence": 207,
  "payload": {
    "message_id": "msg_044",
    "generation_id": "gen_091",
    "delta": "Sure, "
  }
}
```

Followed by:

```json
{
  "version": 1,
  "type": "assistant.message.delta",
  "id": "evt_208",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.300Z",
  "sequence": 208,
  "payload": {
    "message_id": "msg_044",
    "generation_id": "gen_091",
    "delta": "playing Pink Floyd."
  }
}
```

Unlike voice partial transcripts, assistant deltas are incremental and should normally be appended.

```text
voice.transcript.partial
    → replace

assistant.message.delta
    → append
```

This distinction is important.

---

# 23. `assistant.message.completed`

Indicates that the assistant message is complete.

```json
{
  "version": 1,
  "type": "assistant.message.completed",
  "id": "evt_209",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.500Z",
  "sequence": 209,
  "payload": {
    "message_id": "msg_044",
    "generation_id": "gen_091"
  }
}
```

The frontend should mark the corresponding assistant message as complete.

---

# 24. `generation.completed`

Indicates that the generation process has completed.

```json
{
  "version": 1,
  "type": "generation.completed",
  "id": "evt_210",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:12.550Z",
  "sequence": 210,
  "payload": {
    "generation_id": "gen_091"
  }
}
```

This is separate from `assistant.message.completed` because a generation is an execution process and may eventually produce more than one observable artifact.

# 25. `generation.cancelled`

Indicates that an active generation has been cancelled.

```json
{
  "version": 1,
  "type": "generation.cancelled",
  "id": "evt_211",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:32:13.000Z",
  "sequence": 211,
  "correlation_id": "cmd_006",
  "payload": {
    "generation_id": "gen_091",

```

```text

superseded
session_closed
internal_error
```

# 26. Errors

Protocol errors are represented using the `error` event.

Example:

```json
{
  "version": 1,
  "type": "error",
  "id": "evt_300",
  "session_id": "ses_001",
  "timestamp": "2026-11-21T19:35:00.000Z",
  "sequence": 300,
  "correlation_id": "cmd_003",
  "payload": {
    "code": "DRAFT_REVISION_CONFLICT",
    "message": "Draft revision is outdated.",
    "retryable": true,
    "details": {
      "expected_revision": 7,
      "received_revision": 5
    }
  }
}
```

Initial error codes may include:

```text
INVALID_MESSAGE
INVALID_SESSION

DRAFT_NOT_FOUND
DRAFT_REVISION_CONFLICT

GENERATION_NOT_FOUND
GENERATION_ALREADY_COMPLETED

UNAUTHORIZED
RATE_LIMITED

INTERNAL_ERROR
```

WebSocket application errors should use protocol error codes rather than HTTP status codes.

---

# 27. Command Acknowledgement

The protocol should avoid generic acknowledgements for every command.

Whenever possible, the resulting domain event acts as the acknowledgement.

Example:

```text
message.commit
      │
      ▼
message.committed
```

The resulting event contains:

```json
"correlation_id": "cmd_005"
```

A generic `command.accepted` event may be introduced later for commands that do not naturally produce another domain event.

---

# 28. Reconnection and Event Replay

The server assigns a monotonically increasing `sequence` number to events within a session.

Example:

```text
203
204
205
206
207
```

The client stores the last successfully processed sequence.

Suppose the connection is lost after:

```text
sequence = 205
```

while the server produces:

```text
206
207
208
```

After reconnecting, the client sends:

```json
{
  "type": "session.sync",
  "payload": {
    "last_sequence": 205
  }
}
```

If those events are still available, the server replays:

```text
206
207
208
```

before continuing with live events.

The initial implementation may use a bounded in-memory event history.

A persistent event store is not required for protocol V1.

---

# 29. Event Ordering

Events for the same session must be emitted in increasing `sequence` order.

Clients should process events according to `sequence`, not according to local receipt timestamps.

Duplicate events may occur after reconnection.

Clients should therefore be able to ignore events whose sequence has already been processed.

---

# 30. Voice Processing Rules

Speech recognition belongs to the Ermes runtime/orchestrator, not to the frontend.

The frontend may display:

```text
voice.transcript.partial
voice.transcript.final
```

but must not decide when a voice utterance becomes a user message.

For example:

```text
Speech detected
      ↓
voice.transcript.partial
      ↓
wake-word detection
      ↓
more partial transcription
      ↓
silence / orchestrator logic
      ↓
message.committed
```

The orchestrator is the authoritative source for message validity.

---

# 31. Keyboard Drafts

Keyboard drafts may be sent before the user commits the final message.

The frontend should debounce draft updates rather than send every keystroke.

A possible initial interval is approximately:

```text
300–500 ms
```

This value is an implementation detail and is not part of the protocol contract.

Example:

```text
User types
      ↓
debounce
      ↓
draft.update revision 4

User continues typing
      ↓
debounce
      ↓
draft.update revision 5

User presses Enter
      ↓
message.commit revision 5
```

---

# 32. Future Speculative Generation

The protocol is designed to support speculative generation in the future.

For example:

```json
{
  "type": "generation.started",
  "payload": {
    "generation_id": "gen_300",
    "draft_id": "draft_017",
    "draft_revision": 8,
    "speculative": true
  }
}
```

A speculative generation may start before `message.commit`.

However, protocol V1 should not expose speculative assistant deltas to the user.

A speculative result should only become visible after the corresponding draft is committed and the orchestrator confirms that the generation is still valid.

This avoids displaying answers for text that the user has not finished writing.

---

# 33. Heartbeats

WebSocket protocol-level ping/pong should be used to detect dead connections.

Application-level events such as:

```text
app.ping
app.pong
```

are not required in protocol V1.

They may be introduced later if application-visible latency monitoring becomes necessary.

---

# 34. Text vs Binary Frames

Protocol V1 uses JSON text frames.

Binary WebSocket frames are intentionally outside the initial protocol.

In particular, raw real-time audio should not be added to this protocol without separately considering:

- backpressure;
- buffering;
- bandwidth;
- latency;
- codecs;
- cancellation;
- flow control.

The existing audio infrastructure may continue operating independently.

---

| Event | Purpose |
|---|---|
| `session.synced` | Session synchronization completed |
| `draft.updated` | Draft revision accepted |
| `draft.cancelled` | Draft removed |
| `voice.transcript.partial` | Current speech recognition hypothesis |
| `voice.transcript.final` | Final speech recognition result |
| `message.committed` | User message accepted |
| `generation.started` | Response generation started |
| `assistant.message.started` | Assistant message created |
| `assistant.message.delta` | Incremental assistant output |
| `assistant.message.completed` | Assistant message completed |
| `generation.completed` | Generation process completed |
| `generation.cancelled` | Generation cancelled |
| `error` | Protocol or execution error |

# 40. Initial Protocol Scope

Protocol V1 intentionally does **not** define:

- raw audio streaming;
- binary frames;
- file uploads;
- authentication payloads;
- presence;
- multi-user rooms;
- tool-specific event schemas;
- persistent event storage;
- visible speculative responses;
- Redis or distributed event transport.

These concerns can be added later without changing the core command/event model.

# 41. Design Principles

The protocol should follow these principles:

### Commands express intent

```text
message.commit
generation.cancel
```

### Events describe facts

```text
message.committed
generation.cancelled
```

### The orchestrator is authoritative

The frontend displays state but does not reproduce orchestration logic.

### Drafts are mutable

They may change or disappear.

### Messages are immutable

Once committed, they represent conversation history.

### Generations are processes

They are separate from the messages they produce.

### Events are ordered

Server events use monotonically increasing sequence numbers.

### Reconnection is part of the protocol

Clients must be able to recover after transient disconnections.

### Input source should not affect downstream processing

```text
keyboard ─┐
          ├──► committed message ──► generation
voice ────┘
```

### The protocol should remain small

New message types should only be introduced when they represent a genuinely new domain concept.

# 42. Typical Lifecycle

The intended high-level lifecycle is:

```text
CONNECT
   │
   ▼
session.sync
   │
   ▼
SESSION READY
   │
   ├── draft.update
   │
   ├── voice.transcript.partial
   │
   └── ...
   │
   ▼
message.committed
   │
   ▼
generation.started
   │
   ▼
assistant.message.started
   │
   ▼
assistant.message.delta × N
   │
   ▼
assistant.message.completed
   │
   ▼
generation.completed
```

This lifecycle forms the foundation of the Ermes real-time interaction protocol.
